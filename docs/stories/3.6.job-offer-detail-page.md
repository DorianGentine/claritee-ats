# Story 3.6: Job Offer Detail Page

## Status

DONE

## Story

**As a** recruiter,  
**I want** to see full details of a job offer including linked candidates,  
**so that** I can manage the recruitment pipeline for that position.

## Acceptance Criteria

1. Offer detail page with header: title, status badge, client company (linked), contact référent (si défini)  
2. Details section: description, location, salary range, tags, contact client (nom, email, téléphone avec lien copier)  
3. "Modifier" and "Supprimer" buttons  
4. **Candidats section:** List of candidates linked to this offer with their status  
5. Candidate entries show: photo, name, title, status badge  
6. Click on candidate opens candidate detail (or modal)  
7. "Associer un candidat" button to link existing candidates  
8. Empty candidats state: "Aucun candidat associé"  
9. Quick status change dropdown on each candidate row  
10. Count of candidates per status displayed  

**Réf.** PRD § Epic 3, Story 3.6 ; Architecture §5 (JobOffer, ClientCompany, ClientContact, Candidature) ; Design System §2 (statuts offre & statuts candidature, badges) ; Wireframes §5 Fiche Offre (header titre/client/salaire/tags, description, section Candidats associés avec photo/nom/titre/dropdown statut/Dissocier, Notes).

> Note: La création d’associations candidat–offre (bouton "Associer un candidat" et modèle Candidature) est principalement couverte par la **Story 3.7**, et la gestion avancée du statut de candidature (dropdown, filtres) par la **Story 3.8**. Cette story 3.6 se concentre sur la fiche offre et prépare les hooks d’intégration nécessaires.

- **Story 3.1 & 3.2 DONE** : gestion des entreprises clientes et contacts clients (ClientCompany, ClientContact) ; la fiche offre réutilise ces relations pour afficher le client et le contact référent. [Source: docs/stories/3.1, 3.2]

- **Story 3.4 DONE** : création/édition/suppression d’offres (`offer.create`, `offer.update`, `offer.delete`, `JobOfferForm`). La fiche offre s’appuie sur ces procédures pour les boutons "Modifier" et "Supprimer". [Source: docs/stories/3.4]  
- **Story 3.5 DONE** : système de tags pour les offres (`OfferTag`, `OfferTagsSection`). La fiche offre intègre la section Tags fournie. [Source: docs/stories/3.5]  
- **Story 3.7 & 3.8 (à venir)** : association candidats–offre (Candidature) et gestion détaillée des statuts de candidature. La présente story 3.6 prépare les hooks UI/API (section candidats, compteurs par statut, emplacement du bouton "Associer un candidat" et du dropdown de statut) mais délègue la logique métier complète à ces stories. [Source: docs/prd.md Stories 3.7, 3.8]  

### Data Models

- **JobOffer** : `id`, `title`, `description?`, `location?`, `salaryMin?`, `salaryMax?`, `status` (`TODO`, `IN_PROGRESS`, `DONE`), `clientCompanyId?`, `clientContactId?`, `companyId`, `createdAt`, `updatedAt`.  
- **ClientCompany** : `id`, `name`, `siren?`, `companyId`, relations `offers` et `contacts`.  
- **ClientContact** : `id`, `clientCompanyId`, `firstName`, `lastName`, `email?`, `phone?`, `position?`, `linkedinUrl?`.  
- **Tag / OfferTag** : modèles communs aux stories de tags (2.8, 3.5) pour afficher les tags de l’offre.  
- **Candidature** : `id`, `candidateId`, `offerId`, `status`, `createdAt`, `updatedAt` avec contrainte unique (`candidateId`, `offerId`). Utilisée ici en lecture pour afficher les candidats associés et compter par statut ; la création/édition/suppression est couverte en 3.7/3.8.  
- **Candidate** : champs nécessaires pour l’affichage dans la liste (photo, nom, titre).  

### API Specifications

- **offer.getById** :  
  - Input : `{ id: string }` via schéma Zod.  
  - Comportement : retourne une offre du cabinet courant (filtre `companyId = ctx.companyId`) ou une erreur si non trouvée ; inclut `clientCompany`, `clientContact`, `tags` (via Tag/OfferTag) et `candidatures` avec leurs `candidate`.  
  - Output : structure adaptée au frontend (`OfferDetailViewProps` ou équivalent), incluant les compteurs d’agrégation par statut de candidature.  
- **Candidature list by offer** : pas nécessairement une procédure dédiée si inclus dans `offer.getById` ; sinon, prévoir une future procédure `candidature.listByOffer` pour Stories 3.7–3.8.  

### UI & Components

- La fiche offre `/offers/[id]` doit respecter le layout global dashboard (sidebar/header) et réutiliser les composants existants (cards, badges, boutons) définis dans le Design System (palette beige/terracotta/sauge).  
- Le statut de l’offre (badge) doit toujours réutiliser `offer-status-style.ts` pour éviter la duplication de classes.  
- La section Tags réutilise `OfferTagsSection` pour garder une expérience cohérente entre fiche offre et autres vues.  
- La section Candidats doit être pensée comme **extensible** : ajout ultérieur de filtres, dropdown de statut, bouton Dissocier, etc., sans nécessiter une refonte complète.  

### Testing

- Côté back : privilégier les tests d’intégration sur `offer.getById` (multi-tenancy, relations correctement chargées, agrégation des statuts candidature).  
- Côté front : tests unitaires de composants pour `OfferDetailView` et la section candidats, en s’appuyant sur les patterns de `tests/unit/components/offers/JobOfferCard.test.tsx`.  
- QA : les cas de test manuels doivent couvrir les scénarios "offre avec client et contact", "offre sans client", "offre avec/sans candidats", navigation depuis la liste offres et la fiche client.
