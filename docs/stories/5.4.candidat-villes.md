# Story 5.4: Formulaire candidat — Villes (multi, ordonné)

## Status

done

## Story

**As a** recruiter,
**I want** to associate multiple ordered cities to a candidate,
**so that** I can reflect geographic preferences on the profile.

## Acceptance Criteria

1. Formulaire création candidat (`/candidates/new`) : champ `city` (texte) remplacé par `CityAutocomplete` en `mode="multi"`
2. Formulaire édition candidat (`/candidates/[id]/edit`) : même remplacement ; villes actuelles pré-chargées dans le bon ordre
3. Procédure `candidate.create` : accepte `cities: { cityId: string; order: number }[]` (peut être vide)
4. Procédure `candidate.update` : remplace toutes les `CandidateCity` existantes (`deleteMany` puis `createMany`)
5. Schéma Zod mis à jour : `city` retiré, `cities` ajouté (`z.array(z.object({ cityId: z.uuid(), order: z.number().int().min(0) })).default([])`)
6. Fiche candidat (`/candidates/[id]`) : villes affichées dans l'ordre (ex. "Paris · Lyon")
7. Liste candidats (`/candidates`) : affiche la ville `order=0` du candidat, ou vide si aucune
8. Include `cities { city: true, order: true }` trié par `order asc` dans `candidate.getById` et `candidate.list`
9. Tests : create avec 2 villes + vérification ordre en base ; update remplace correctement ; create sans villes fonctionne

## Review Findings (2026-07-19)

- [x] [Review][Patch] Sémantique `update` → patch-semantics (décidé le 2026-07-19) [src/server/trpc/routers/candidate.ts:272] — `cities` devient `.optional()` **sans** default sur `updateCandidateSchema` ; le `deleteMany`/`createMany` ne s'exécute que si `cities !== undefined`. Aligne les villes sur la sémantique patch des champs scalaires et supprime le footgun d'effacement silencieux. (`createCandidateSchema` garde son `default([])`.)
- [x] [Review][Patch] Atomicité des écritures villes (create + update) [src/server/trpc/routers/candidate.ts:275] — écritures multi-étapes hors `$transaction` : si `createMany` échoue (FK `cityId`, contrainte unique), l'`update` a déjà supprimé les villes existantes → perte de données ; le `create` laisse un candidat persisté sans villes alors que le client reçoit une erreur. Envelopper dans `$transaction`. Note : la spec dit « $transaction pas nécessaire », mais visait l'incompat `groupBy`, pas l'atomicité — ce cas n'était pas couvert.
- [x] [Review][Patch] Input villes non durci côté serveur [src/lib/validations/candidate.ts:532] — `cityId` dupliqué → P2002 500 brut ; `cityId` inexistant → P2003 500 brut ; `order` non contraint en unicité/contiguïté rend la ville principale (`take: 1`, `orderBy order asc` en liste) non déterministe. L'UI garde déjà les doublons, mais la frontière tRPC reste exposée. Ajouter un `.refine` d'unicité `cityId` (et éventuellement `skipDuplicates` sur `createMany`).
- [x] [Review][Patch] Assertions unitaires affaiblies [__tests__/unit/lib/validations/candidate.test.ts:232] — `toEqual`→`toMatchObject` (3 cas) : ne détecte plus les champs inattendus injectés par le schéma. Asserter l'objet complet, `cities: []` inclus.

### Data Models

```
CandidateCity {
  id          String   (PK uuid)
  candidateId String   (FK Candidate, onDelete Cascade)
  cityId      String   (FK City, onDelete Restrict)
  order       Int      (0-based)
  @@unique([candidateId, cityId])
}
```

**Pattern delete+createMany pour `update` :** Prisma ne gère pas nativement la mise à jour d'une liste ordonnée N-N. Le pattern delete+createMany est la bonne approche ici. Pas besoin de `$transaction` (pas de `groupBy` concerné).

### API Specifications

**`candidate.create` input (extrait) :**
```ts
cities: z.array(z.object({ cityId: z.uuid(), order: z.number().int().min(0) })).default([])
```

**`candidate.list` output (extrait) :**
```ts
cities: [{ city: { id, name, region, country }, order: 0 }]  // take: 1, orderBy order asc
```

**`candidate.getById` output (extrait) :**
```ts
cities: [
  { city: { id, name, region, country }, order: 0 },
  { city: { id, name, region, country }, order: 1 },
]
```
