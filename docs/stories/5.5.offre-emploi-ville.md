# Story 5.5: Formulaire offre d'emploi — Ville unique

## Status

done

## Story

**As a** recruiter,
**I want** to associate a single structured city to a job offer,
**so that** offers have consistent, filterable locations.

## Acceptance Criteria

1. Formulaire création offre : champ `location` (texte) remplacé par `CityAutocomplete` en `mode="single"`
2. Formulaire édition offre : même remplacement ; ville actuelle pré-chargée si définie
3. Procédure `jobOffer.create` : `location` retiré, `cityId: string | null` ajouté
4. Procédure `jobOffer.update` : même changement
5. Schéma Zod mis à jour : `location` retiré, `cityId` ajouté (`z.uuid().optional().nullable()`)
6. Détail offre (`/offers/[id]`) : affiche "Nom de la ville, Région" ou rien si `cityId` null
7. Liste offres : affiche la ville de l'offre si définie
8. Include `city: true` dans les queries Prisma `jobOffer.list` et `jobOffer.getById`
9. Tests : create offre avec `cityId` ; update `cityId → null` efface la ville

### Data Models

```
JobOffer {
  ...
  cityId    String?   (FK City, onDelete SetNull)
  city      City?     (relation)
  ...
}
```

La ville est optionnelle sur une offre (`cityId String?`). Une offre peut ne pas avoir de ville définie.

### API Specifications

**`jobOffer.create` input (extrait) :**
```ts
cityId: z.uuid().optional()  // undefined = non fourni ; pas de `.nullable()` — rien à déconnecter en création
```

**`jobOffer.update` input (extrait) :**
```ts
cityId: z.uuid().optional().nullable()  // undefined = non fourni (ville inchangée) ; null = explicitement sans ville (déconnecte)
```

**Note (revue 2026-08-15) :** la spec initiale documentait `cityId` nullable dès `create`, mais l'implémentation livrée aligne `create` sur les champs frères (`clientCompanyId`, `clientContactId`), non-nullable en création. Comportement confirmé intentionnel — seule cette note a été corrigée, aucun changement de code.

**`jobOffer.getById` output (extrait) :**
```ts
city: { id, name, region, country } | null
```
