## Story

**As a** recruiter,
**I want** to associate multiple cities to a client company,
**so that** I know which locations a client operates in.

## Acceptance Criteria

1. Formulaire création entreprise cliente : `CityAutocomplete` en `mode="multi"` ajouté — les boutons ↑↓ ne s'affichent pas (pas d'ordre pour `ClientCompanyCity`)
2. Formulaire édition entreprise cliente : même ajout ; villes actuelles pré-chargées
3. Procédure `clientCompany.create` : accepte `cityIds: string[]` (peut être vide)
4. Procédure `clientCompany.update` : remplace toutes les `ClientCompanyCity` (`deleteMany` puis `createMany`)
5. Schéma Zod mis à jour : `cityIds` ajouté (`z.array(z.uuid()).default([])`)
6. Fiche entreprise cliente (`/clients/[id]`) : villes affichées comme badges (sans ordre imposé)
7. Include `cities { city: true }` dans `clientCompany.getById`
8. Tests : create avec villes ; update remplace les villes ; create sans villes fonctionne

## Dev Notes

### Previous Story Insights

- Story 5.1 : modèle `ClientCompanyCity` créé en base (`@@id([clientCompanyId, cityId])` — pas d'`id` auto, pas d'`order`)
- Story 5.3 : `CityAutocomplete` disponible

### Data Models

```
ClientCompanyCity {
  clientCompanyId  String   (PK, FK ClientCompany, onDelete Cascade)
  cityId           String   (PK, FK City, onDelete Restrict)
  @@id([clientCompanyId, cityId])
}
```

Pas d'`order` : `ClientCompanyCity` est une liaison N-N pure. Les villes s'affichent sans ordre particulier.

### API Specifications

**Gestion des boutons ↑↓ dans `CityAutocomplete` :**  
Le composant `CityAutocomplete` affiche les boutons ↑↓ en mode multi. Pour `ClientCompany` où l'ordre ne compte pas, deux options :
- **Option A (préférable)** : ajouter une prop `ordered?: boolean` (défaut `true`) sur `CityAutocomplete` — si `false`, les boutons ↑↓ ne sont pas rendus
- **Option B (acceptable)** : ignorer l'ordre retourné par `onChange`, utiliser simplement les IDs

Préférer l'option A pour l'UX (évite une confusion pour le recruteur).
