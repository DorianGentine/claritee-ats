# Story 5.1: Infrastructure DB — Table City & Migration

## Status

review

## Story

**As a** developer,
**I want** the database to have a structured `City` model with all required relations,
**so that** the rest of the epic can build on a clean data foundation.

## Acceptance Criteria

1. Modèle Prisma `City` créé : `id`, `name`, `region?`, `country`, `latitude`, `longitude`, `createdAt` — table `cities` sans `companyId` (données de référence globales)
2. Modèle `CandidateCity` créé : `id`, `candidateId`, `cityId`, `order` — contrainte `@@unique([candidateId, cityId])`
3. Modèle `ClientCompanyCity` créé : `@@id([clientCompanyId, cityId])` (pas d'ordre)
4. `Candidate.city` (String?) supprimé ; relation `cities CandidateCity[]` ajoutée
5. `JobOffer.location` (String?) supprimé ; `cityId String?` (FK vers `City`) ajouté
6. `@@index` sur `Candidate` mis à jour (retrait du champ `city` devenu inexistant)
7. Migration Prisma générée (`pnpm db:migrate`) et appliquée sans erreur
8. Extensions PostgreSQL activées via migration SQL brute : `unaccent`, `pg_trgm`
9. Index GIN créé dans la migration : `CREATE INDEX idx_cities_name_trgm ON cities USING gin (unaccent(name) gin_trgm_ops)`
10. Script `scripts/seed-cities.ts` créé, appelle Photon pour ~250 grandes villes européennes avec délai 200ms entre appels
11. `pnpm db:seed` exécute le seed sans erreur ; idempotent (upsert sur `name + country`)

## Dev Notes

### Previous Story Insights

Premier epic post-MVP. Aucune story précédente dans cet epic. Le schéma Prisma actuel est en production (Supabase). La migration supprime des colonnes existantes — vérifier d'abord sur l'environnement de développement.

**Stratégie migration données :** table rase. Les valeurs texte de `Candidate.city` et `JobOffer.location` sont abandonnées. Ne pas écrire de script de mapping.

### Data Models

**Avant :**
- `Candidate.city String?`
- `JobOffer.location String?`
- `ClientCompany` : pas de champ ville

**Après :**
- `City` : table globale partagée (pas de `companyId`)
- `CandidateCity` : liaison N-N avec ordre — `onDelete: Cascade` sur candidateId, `onDelete: Restrict` sur cityId (une ville ne peut pas être supprimée si des candidats y sont liés)
- `ClientCompanyCity` : liaison N-N sans ordre — mêmes règles de cascade
- `JobOffer.cityId String?` : FK nullable, `onDelete: SetNull`

### API Specifications

Aucune procédure tRPC dans cette story — uniquement infrastructure DB et seed. Les procédures sont créées en 5.2.

### File Locations

| Fichier | Action |
|---------|--------|
| `prisma/schema.prisma` | Modifié (3 nouveaux modèles, 2 champs supprimés, index mis à jour) |
| `prisma/migrations/20260614000000_city_structured/migration.sql` | Créé (extensions + index GIN manuels) |
| `scripts/seed-cities.ts` | Créé |

### Technical Constraints

- Extensions `unaccent` et `pg_trgm` doivent être activées **dans la migration** (pas dans le seed) pour que l'index GIN fonctionne
- `onDelete: Restrict` sur `CandidateCity.cityId` et `ClientCompanyCity.cityId` : une ville référencée ne peut pas être supprimée — cohérence des données
- Supabase : les extensions Postgres sont autorisées via `CREATE EXTENSION IF NOT EXISTS` dans les migrations
- Le seed utilise `tsx` pour exécuter du TypeScript directement — vérifier que `tsx` est disponible (`pnpm add -D tsx` si absent)

### Testing

- Vérifier que la migration s'applique proprement : `pnpm db:migrate`
- Vérifier que le seed tourne jusqu'au bout sans crash
- Vérifier dans Supabase Studio que la table `cities` contient bien les villes seedées
- Vérifier l'index GIN : `SELECT indexname FROM pg_indexes WHERE tablename = 'cities'`
