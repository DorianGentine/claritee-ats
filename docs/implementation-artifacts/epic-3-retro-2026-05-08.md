# Rétrospective — Epic 3 : Offres, Clients & Pipeline

**Date :** 2026-05-08  
**Facilitatrice :** Amelia (Senior Software Engineer)  
**Participants :** Dorian (Project Lead), Winston (Architect), Sally (UX Designer)  
**Stories reviewées :** 3.1 → 3.12 (12/12 complétées ✅)

---

## Résumé de livraison

- **Vélocité :** 12 stories livrées — le plus large epic du projet
- **Complexité :** BlockNote rich text editor, FAB widget avec état persistant, auto-save debounce, déplacement de notes cross-entités
- **Patterns consolidés :** shared `NotesSection`, `candidature` router séparé, optimistic UI avec `networkMode: "always"`

---

## Ce qui a bien marché

- **Notes en style chat (Story 3.9).** La spec originale prévoyait une modal. L'implémentation a opté pour un formulaire fixe en bas et des bulles type fil de discussion (ordre asc). UX nettement supérieure à la spec — et cohérente avec le widget Story 3.11.
- **`NotesSection` partagé (Story 3.10).** Extraction du composant notes en composant partagé entre candidats et offres — DRY respecté sans sur-ingénierie.
- **Séparation `candidature.ts` / `offer.ts` (Story 3.8).** La décision de créer un router dédié pour les candidatures (plutôt que d'étendre `offer`) était la bonne pour la responsabilité unique. Les tests sont plus clairs.
- **Optimistic UI avec `networkMode: "always"` (Story 3.8).** Pattern capturé et documenté dans `docs/architecture/coding-standards.md` — réutilisable dans Epic 4.
- **FAB widget avec état persistant (Story 3.11).** `NoteWidgetProvider` conserve l'état lors de la navigation — bonne UX sans complexité excessive.

---

## Défis & zones d'amélioration

- **12 stories d'un coup** est le plus grand epic. Plusieurs stories ont des dépendances fortes (3.9 → 3.10 → 3.11 → 3.12 sont un pipeline notes complet). Si une story avait rencontré un problème bloquant, l'ensemble du pipeline notes aurait été impacté.
- **`moveToOffer` UI non implémentée (Story 3.12).** L'API `note.moveToOffer` est prête mais le dropdown dans "Mes notes" n'a pas été ajouté. Découverte : `offer.list` n'était pas disponible dans le contexte de la page au moment du développement, ce qui a mené à la décision de reporter. → Adressé en Story 4.9.
- **`window.confirm()` propagé depuis Epic 2.** Les suppressions de notes, contacts et candidatures utilisent toujours `window.confirm()`. → Adressé en Story 4.9.
- **Rate limiting absent sur les mutations offres, notes, clients, candidatures.** → Adressé en Story 4.9.
- **Auto-save sans feedback visuel (Story 3.11/3.12).** L'auto-save debounce 2s est silencieux — pas d'indicateur "Enregistrement..." visible. Acceptable pour le MVP.

---

## Insights clés

1. **Les specs UI méritent d'être challengées avant l'implémentation.** Notes en modal vs chat : la question aurait pu être posée avant le dev pour aligner spec et implémentation. À partir d'Epic 4, si une spec UI semble sous-optimale, la questionner avant de coder.
2. **Un epic de 12 stories est à la limite du gérable en solo.** Découper Epic 3 en deux (3a : Clients + Offres, 3b : Notes + Pipeline) aurait réduit le risque de blocage en cascade.
3. **Les dépendances API cross-stories doivent être identifiées en Task 0.** `offer.list` manquait dans la Story 3.12 — ce genre de dépendance doit être vérifié avant de commencer l'implémentation, pas découvert en cours.
4. **`networkMode: "always"` est obligatoire pour toute mutation optimiste.** Documenté dans `coding-standards.md` — ne pas oublier dans Epic 4.
